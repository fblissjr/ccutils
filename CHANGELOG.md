# Changelog

All notable changes to this project will be documented in this file.

## [Unreleased]

### Fixed
- **`--dry-run`, `-q`, `-j`, `--batch-size`, `--no-search-index` were accepted and ignored outside `--source`, and `--flat` / `--expand-chains` outside the picker.** `ccutils session.jsonl --dry-run -q` wrote files and printed output -- a dry run that creates things and a quiet run that talks. Ignoring `--dry-run` is the worst of the set, because it produces writes rather than a no-op. All now `UsageError`, matching `--embed` / `--llm-facets` / `--private`. Checked against click's parameter source, so a default never trips the guard.
- **A scoped build left the prompts an earlier unscoped build had already inserted.** `import_history` is insert-only, and both the picker and `--source` default to the same directory, so building a full archive and then a scoped one -- the README's own two commands in order -- produced a warehouse that reported itself scoped while still holding every prompt on the machine. Scoping is now a state of the warehouse, not a filter on new inserts; out-of-scope and unattributable rows are removed. Safe because `dim_prompt` is derived and an unscoped run re-imports it.
- **The prompt-history import was a bare call inside `except Exception: pass`, with no lineage row.** CLAUDE.md has named this one out for a while ("`dim_prompt` is still un-wrapped -- fix it when touched"); it was touched twice this release. A warehouse whose import raised mid-parse, or whose scope matched nothing, looked exactly like one built where no `history.jsonl` existed. It now records a `global_source` run and a `dim_prompt` step like the memory import beside it, and records rather than re-raises because history is additive. Wiring the count exposed a second bug: `import_history` returned `.rowcount`, which DuckDB leaves at -1 for DML, so the count had always been wrong and nothing noticed until it became a step count.
- **`-o archive.duckdb` as a bare name put `parquet_lake/` in the cwd** -- the escape hatch reinstating the exact behaviour the directory rule exists to prevent. The path is resolved before its parent is taken.
- **A picker run with no `-o` overwrote a full archive's master index.** Both write `index.html` into the same home-anchored directory, so a two-session pick replaced the archive's index with a two-card one; the transcripts survived, the way back to them did not. Picks now land in a `picked/` subdirectory.

### Changed
- **The contract canary for claim 2 now runs the ETL** instead of asserting a list comprehension against a dict literal it had just written. The previous version executed no ccutils code and would have passed had the SQL projection dropped every text block -- the shape the same morning's test audit classifies as decorative. Verified by mutation: nulling `content_text` in the projection turns it red.
- **Several named PATHS were converted as N separate runs into one shared output, and the later ones overwrote the earlier.** `ccutils a.jsonl b.jsonl -o ./out` -- the command's own help example -- wrote both transcripts but rebuilt `index.html` from the last file alone, so the first was unreachable. `--format json` was worse: `dimensions/` was overwritten per file and only the last session survived, exit 0. It also produced N `fact_etl_batch_runs` rows for one invocation, ran the global sources N times, and with no `-o` opened a browser window per file. Now one pipeline run for all named files, which is what the shared output implies.
- **`--format markdown -o notes.md` crashed with `IsADirectoryError` on any session with subagents.** The `.md` single-file case was keyed on `len(session_files) == 1`, which stopped being true the moment single-file conversion started attaching agent transcripts: `mkdir` created a *directory* named `notes.md` and the renderer then opened it as a file, leaving the stray directory behind. It is now keyed on what the user asked for -- attaching subagents must not change how `-o notes.md` is interpreted.
- **`--format json -p <project>` still exported every prompt on the machine.** `generate_json_archive` forwards ten arguments to the duckdb builder and `scope_history` was not among it, so the scoping shipped in the previous entry never reached the most shareable output format ccutils produces. Forwarded.
- **The project-directory encoder replaced only `/`, not `.` and `_`.** Claude Code collapses all three, so the encoded-match arm never fired for any path containing a dot or underscore -- verified on the real corpus, where a cwd ending `/evalroot/_run_d90fe13e` lives in a directory ending `-evalroot--run-d90fe13e`. Those projects' prompts were silently dropped from scoped builds. Re-measuring the match rate with the corrected encoder gives 89.0% against the 88.9% published previously, so the figure that justified leaving full-corpus builds unscoped stands; the bug it came from did not.
- **A warehouse built for one project carried every prompt on the machine.** `history.jsonl` is machine-wide and was imported unscoped, so a single-session warehouse for one project held **11,606 prompts from 103 projects** -- measured, not hypothetical. That contradicts this project's own privacy boundary: a shared artifact is SCOPED, not scrubbed, so an export generated for named projects must contain nothing else, and the llm-wiki goal is precisely to hand these to agents. `_import_auto_memory` already scoped correctly off `dim_project`; history did not, despite every entry carrying the project path needed. It now does, and the same one-session build yields 629 prompts from one project. The leak predates the 0.20.0 global-sources change on the batch path (`--source -p project` already leaked); that change widened it to every path.
- **Scoping follows caller intent, because scoping a full-corpus build is not the no-op it looks like.** Measured: forward-encoding matches 88.9% of history entries to a project directory, so always-on scoping would silently drop the other 11% from a full build -- prompts typed in directories that never became a session, or whose project has since been pruned. So a subset build (named paths, picker, or `-p`) scopes; an unfiltered `--source` does not. Taking too much is a privacy problem only where a subset was requested; dropping rows is a data-loss problem everywhere.
- **Project matching encodes forward rather than decoding backward.** Claude Code's dashed directory name is lossy in the decode direction: a dashed name decodes to a path with extra separators, a different and nonexistent path, so a first cut silently dropped every prompt for any project whose name contains a dash. Entries are now matched by encoding their real path forward and comparing, plus an exact `dim_session.cwd` match. No prefix or substring logic, per the resolver rule this project already follows.

### Changed
- **The global sources take an injected `claude_home`** instead of reading `Path.home()` internally. Warehouse-building tests no longer depend on the developer's machine state or parse a multi-megabyte real history file.
- **The JSONL contract's one-block-per-assistant-entry claim was an absolute, and it is not one.** Its own canary caught it: written from a 120-file sample containing zero violations, it went red hours later on a different draw. Corpus-wide the real figure is **17 violations in 198,230** assistant entries (0.0086%), including entries mixing `text` with `thinking` and `tool_use`. A 0.009% event is invisible in 120 files roughly always -- a rare-event claim cannot be established by a sample smaller than the event's inverse rate. The claim is now stated as a rate with the measurement behind it, and the canary asserts the rate stays negligible while scanning the whole corpus rather than sampling. Verified separately that the tail is handled correctly: an entry containing `[text, thinking, tool_use, text]` yields both prose blocks in `content_text`, so nothing is dropped. The substantive consequence is unchanged -- a NULL `content_text` on a tool-carrying row is still the format rather than a loss -- but the margin is 0.009%, not zero.
- **Jinja2 `autoescape` was the only control escaping template interpolation, and nothing tested it.** Flipping it off put a live `<script>alert(1)</script>` into generated HTML from attacker-controlled transcript fields -- session id, cwd, git branch, model name, tool name, tool input -- while all 162 render tests stayed green. The suite's existing XSS tests cover `render_markdown_text`, which is a different channel: markdown runs with `html=False` and escapes raw HTML itself, so those tests pass whether autoescape is on or off. `nh3` does not cover it either; the codebase's own comment calls nh3 defence-in-depth over a renderer already configured safe, and measurement confirms it changes nothing dangerous. New test `test_template_interpolation_escapes_transcript_content` passes on correct code and fails on exactly that mutation, and additionally asserts the payload stays visible as escaped text rather than being dropped. Found by the test audit's second pass.
- **Five columns existed only in `_COLUMN_MIGRATIONS` and in no `CREATE TABLE`, and would have vanished when that list is deleted.** `fact_agent_delegations.agent_resolved_model`, `.agent_is_async`, `.completion_state`, `.agent_derived_io_tokens` and `fact_etl_runs.run_kind`. This was invisible because migrations run after the CREATEs on every `create_star_schema()` call, so fresh and existing warehouses both got the column from the ALTER and nothing distinguished them. Since 1.0.0 deletes `_COLUMN_MIGRATIONS` wholesale under the no-migration rule, all five would have disappeared from every fresh warehouse at that moment -- and `completion_state` is the column the delegation reconciliation pass keys every rollup on, so the symptom would have been "delegation outcomes silently stop working" rather than an error. Each is now declared in its table's CREATE, with a test (`TestCreateTableIsSelfSufficient`) asserting the two stay in sync so a sixth cannot appear before the deletion. Both paths verified: a fresh warehouse gets all five from the CREATE, an older one still heals via the ALTER, and the column sets match.

## [0.20.0]

### Changed
- **One conversion command replaces `local` and `all`; `web` and `schema` are removed.** `ccutils` with no arguments picks sessions interactively, `ccutils PATHS...` converts exactly the files named, and `ccutils --source` walks every session under a directory. `local` and `all` were one operation split by scope, and the split is what let their behaviour drift: global post-loop sources ran on one path and not the other, so the two produced warehouses of different shapes. `convert` stops being a hidden duplicate and becomes the name of the single conversion command. `web` and `schema` are deleted outright -- one read a different data source through an undocumented API behind a keychain token, the other was a generic JSON introspector, and neither had a path to the warehouse.
- **Removed names fail with a pointer instead of silently redirecting.** This needed doing explicitly: `click_default_group` forwards an unknown token to the default command, so `ccutils local --help` printed the *conversion* help and exited 0, which reads as "still supported" to anyone checking. `local`, `all`, `web` and `schema` now exit 2 and name the replacement, or say plainly that there is none.
- **`--no-agents` and `--with-llm-facets`/`--batch-llm-facets` collapse into `--no-subagents` and `--llm-facets`.** They were the same behaviours under different spellings on the two commands.

### Fixed
- **`-o` names a directory everywhere.** It was a path stem for duckdb: `-o DIR/e` wrote `DIR/e.duckdb` and dropped `parquet_lake/` in `DIR` -- two things beside the path you named rather than inside it, with the lake in particular landing wherever you happened to be standing. `-o DIR` now yields `DIR/archive.duckdb` + `DIR/parquet_lake/`, matching what the batch path already did. A path ending in `.duckdb` is still honoured, since typing one is the obvious thing to try.
- **`--embed` and `--llm-facets` fail loudly on formats that cannot use them.** `--embed` was accepted and ignored on every render format -- exit 0, no embeddings, no message -- and on the single-file path in *any* format, because the conversion helper was never passed it. `--llm-facets` was worse than ignored: the extractor was built before the format was dispatched, so an HTML export demanded an `ANTHROPIC_API_KEY` and exited 2 on a credential that format would never use. Both checks now run before any credential resolution, so the rejection is about the format and does not depend on having a key. `--private` on duckdb/json was already the model for this.
- **Every path that builds a warehouse now builds the same one.** The three global sources -- delegation reconciliation, `dim_prompt` from history.jsonl, and auto memory -- lived inline in the batch exporter, and the single-session path ran only the first. So `ccutils <file> --format duckdb` produced a warehouse with `fact_messages.prompt_id` populated against an empty `dim_prompt`, and no memory tables at all; an external audit reported that as an ETL defect when it was an entry-point defect. They now live in `etl/global_sources.py` and both callers make one call. Verified on a real session: `dim_prompt` 0 to 11,571, `dim_memory` 0 to 14, `bridge_memory_link` 0 to 30. Error handling stays per-source and deliberate -- reconciliation re-raises because a silent failure there reports spawn-acknowledgment latency as agent duration, history is best-effort, memory records its own failure.

### Documentation
- **README, `docs/`, `CLAUDE.md` and the skill references all updated to the new surface**, and every `ccutils ...` invocation in the README is now checked to actually parse -- 27 of them, all accepted. Stale references to `ccutils all` / `ccutils local` and to the old `--with-llm-facets` / `--batch-llm-facets` / `--no-agents` spellings are gone from `docs/STAR_SCHEMA.md`, `docs/FACET_CLUSTER_PIPELINE.md` and three files under `.claude/skills/`.

### Added
- **`ccutils open`** launches `duckdb -ui` against a built warehouse. It launches, it does not build -- the README's no-SQL-UI boundary holds. With no warehouse present it says so and prints the command that would create one, rather than opening a UI on nothing, which reads as "there is no data" instead of "you have not built it yet".

### Fixed
- **`ccutils session.jsonl` dropped the session's subagents, and opened an `index.html` it never wrote.** Both defects sat on the README's headline invocation. `_convert_file` built no `agent_map`, so the discovery fix in 0.19.1 never reached this path -- a session with four agent transcripts beside it exported one file and said nothing about the rest. It now attaches them exactly as the picker does, and `--no-subagents`, which was accepted here and did nothing, excludes them. Separately, the single-file branch wrote only `<stem>.html` while `maybe_open_browser` opens `<output>/index.html` unconditionally; with no `-o` the browser opens automatically, so the default invocation opened a file that was never created. An index is now written even for a lone session. Verified on a real session: one HTML file before, six with a working index after. The test that covered this path asserted exit code 0 and the string "Output:", which the broken behaviour satisfied exactly -- the new tests assert the files that must exist.

## [0.19.2]

### Fixed
- **Agent lineage was flattened: `depth_level` read 1 on every row while 235 agents on disk stated a parent the warehouse ignored.** Depth was derived by walking `sessionId`, and every agent inherits the ROOT session's `sessionId` (`docs/JSONL_CONTRACT.md` claim 1), so the walk structurally could not produce a value above 1 -- a sub-agent was attributed to the top-level session rather than to the agent that launched it, making fan-out uncountable and overstating what a root session launched. Nesting is stated, not derivable: of 241 agents with `spawnDepth > 1`, 235 carry `parentAgentId`, all resolving to a sidecar in the same directory whose own `spawnDepth` is exactly one less, and no depth-1 agent carries one. `parent_session_key` now comes from `parentAgentId` when stated and the root otherwise, and the existing depth walk produces correct depth as a consequence. Verified on a real 34-file tree: `depth_level` reaches 2 for the first time, one agent is parented to another agent, and stated `spawn_depth` agrees with walked `depth_level` on every row.
- **Workflow-tool agents were ingested as ordinary sessions.** The ETL path rule required `subagents` to be the file's immediate parent, so the 34 agents at `<parent-uuid>/subagents/workflows/<wf-id>/agent-<id>.jsonl` got no `is_agent`, no `agent_id` and no parent -- the ETL-side counterpart of the discovery defect fixed in 0.19.1. `SUBAGENT_PATH_RE` and both SQL tail builders now allow grouping directories below `subagents`, from the one source in `etl/utils.py` that every consumer builds from.

### Added
- **A delegation's final report is re-derived from the agent's own transcript.** On a background launch -- the default since Claude Code v2.1.198 -- `agent_output_text` holds the launch acknowledgment rather than the work, and is deliberately NULL, so the warehouse recorded that work was delegated and nothing about what came back. The agent's terminal assistant message is already in the warehouse, and `populate_delegation_completion` already joins to it for tokens and duration; `agent_derived_output_text` now carries the text. It follows the provenance rule this table already states for tokens -- a STATED value and a DERIVED one never share a column -- so `agent_output_text` still means "what the parent was told at spawn time" and reading either tells you which you have. Written only for `completion_state = 'completed'`, because an unfinished agent's last message is indistinguishable from a finished one's. Verified on a real 33-delegation tree: final reports present on 27, up from 1, and on exactly the completed rows.
- **Every field the agent sidecar states is now read rather than re-derived.** `dim_session` gains `spawn_depth`, `parent_agent_id`, `spawn_tool_use_id`, `agent_model`, `is_fork`, `agent_name`, `worktree_path`, `worktree_branch` and `stopped_by_user`. Two of these settle questions the roadmap had open: `agent_model` is stated on 313 sidecars, which falsifies the claim that the parent's `toolUseResult.resolvedModel` is the only place a subagent's model is recorded; and `spawn_tool_use_id` is the corroborating delegation join key that roadmap 0d asked for, present on 1,146. Where a sidecar states nesting but omits `parentAgentId` (6 of 241 real cases), the root stays the parent and no edge is invented -- `spawn_depth` disagreeing with `depth_level` is a true statement about what the source said, and is what an audit check is for.

## [0.19.1]

### Fixed
- **Subagent transcripts were missing from exports, in four separate ways.** `find_agent_sessions` globbed `agent-*.jsonl` in the session's *own* directory -- the pre-2026 layout. Agents have since lived one directory down, at `<project>/<parent-uuid>/subagents/agent-<id>.jsonl`, so the function matched nothing on real data and the picker path exported subagents for nobody, silently, with `--no-subagents` the only behaviour available. The search now roots at `<parent>/<stem>/subagents` and walks down from there. Ownership comes from the directory, never from the transcript's `sessionId` (agent entries carry the PARENT's on every line, so that field cannot tell two agents apart). Verified end to end: two real sessions that previously ingested 0 agent sessions and resolved 0 of their delegations now ingest 17 and resolve 7 of 7.
- **`recursive=` on `find_agent_sessions` no longer claims to select anything.** It is retained as an accepted keyword and documented as a no-op: measured across 300 real transcripts, every agent carries its root parent's `sessionId` and nested agents (sidecar `spawnDepth` up to 5) sit flat beside their level-1 siblings, so depth is not derivable from the files this function reads. The old `recursive=False` path returned a subset that depth never defined. Stated depth lives in each agent's `.meta.json` `spawnDepth`.
- **Agent transcripts summarising to "(no summary)" were dropped from html and markdown.** A delegated task arrives as a user entry flagged `isMeta`; `_get_jsonl_summary` skips isMeta entries, which is right for a parent session (harness injections) and wrong for an agent transcript, where that entry is the task. Those agents then summarised to "(no summary)" and render-format curation discarded them. Agent files -- identified by the stem, per the subagent identity rule -- now accept that entry. Over a 400-file random sample of real agent transcripts, 23 summarised to "(no summary)"; 17 recover. `Warmup` agents are still curated out, and isMeta entries on ordinary sessions are still skipped.
- **Workflow-tool agents were attributed to a project named after the workflow.** They nest one directory deeper -- `<parent-uuid>/subagents/workflows/<wf-id>/agent-<id>.jsonl` -- and both mirrors of the project-boundary rule stripped only `/<seg>/subagents` layers. `project_dir_sql` now drops the filename and then everything from the first `/<seg>/subagents` onward, which collapses nested delegation in one pass and tolerates any grouping directory below `subagents`; the Python walk-up in `find_all_sessions` cuts at the last `subagents` segment for the same reason. Both were wrong identically, so `TestProjectRuleEquivalence` stayed green -- an agreement check cannot see a shared blind spot. It now sits beside an expected-value oracle that pins the project directory for each layout independently of both implementations.
- **Dead agent-labelling branch removed from the multi-session index.** `generate_multi_session_index` tested a session *stem* against a Path-keyed `agent_map`, so it never fired; repaired literally it would have labelled parent sessions "agent". The `agent-` filename prefix is the label's only source. `agent_map` stays in the signature for call compatibility and is documented as not affecting output.

### Changed
- **Archives no longer default into the current directory: with no `-o`, output goes to `~/.ccutils/claude-archive`.** Both entry points defaulted to `./claude-archive` (`ccutils all` via a click default, `ccutils` picker mode via a literal), so a default run started from inside a checkout deposited unredacted transcripts for *every* project on the machine into that worktree -- guarded by one `.gitignore` line here, and by nothing at all in any other repo. The data is machine-wide and the tool is routinely run from wherever the user happens to be standing, so cwd is the one place the default must never be. Both sites now resolve through `default_archive_output()` (`cli/utils.py`), which is home-anchored, absolute, and evaluated per call rather than at import so the current home directory is honored. `-o/--output` overrides exactly as before, and single-file conversion with no `-o` still uses a temp dir. The `.gitignore` entry stays as belt and braces. New tests (`tests/test_archive_output_default.py`) pin both entry points end to end -- archive absent from cwd AND present under the default, so the absence assertion cannot pass because the export silently did nothing; all four claim-bearing cases were verified red against the old cwd-relative default.

## [0.19.0]

### Fixed
- **The index-edge fix was itself broken on upgrade -- edges relinked but never resolved.** `_sync_links` inserts bridge rows with `target_memory_id` NULL and resolution runs separately, but both resolvers sat after `if not inbound: return 0` -- and the relink path is exactly the case where `inbound` is empty. So the upgrade this whole mechanism exists for produced edges that were present, unresolved and unusable: `semantic_memory_links` showed them with NULL target and NULL project. Worse, self-sealing -- the next run finds stored == wanted, returns early, and the rows stay dead until some unrelated memory changes. Missed because the verification checked that markdown edges APPEARED, never that they RESOLVED, and the test asserted `COUNT(*)` for the same reason: a test written from the same premise as its code cannot falsify that premise. The resolvers now run on the relink path, and the tests assert through `semantic_memory_links` -- the surface a consumer actually reads -- so an unresolved edge fails as the NULL names it really is.
- **A relink-only run reported zero work at every grain.** `rows_inserted` counts versions written, which is zero on exactly the path that rewrites edges corpus-wide, so a DELETE + INSERT + `link_count` UPDATE across every memory recorded as nothing happening. Directly contradicted the operator guidance shipped alongside it, which points at that step to see what the import did. Relink work now reports through `rows_updated`.
- **`record_source` changed value with no backfill.** Rows now carry `claude_code_memory`; every row written before it kept `<auto-memory>`, which is not in `_RECORD_SOURCES`, so `record_source_label()` raises on it and any query filtering the new value silently misses the history. The `run_kind` precedent was followed for `link_syntax` in the same change and not for this. Backfilled on open; the guard test now checks every distinct value in both tables rather than one arbitrary row.
- **Narrowing `except BaseException` left a stuck `running` run row.** Handling only `(KeyboardInterrupt, SystemExit)` and `Exception` meant anything else -- `asyncio.CancelledError`, a harness `Exit` -- escaped without `run.fail()`, leaving `fact_etl_runs` at `status = 'running'` with a NULL `completed_at` forever, which is the untraceable state the wrapper exists to prevent.
- **Index edges never materialised on an upgraded warehouse.** `content_hash` covers a memory's CONTENT, and links are derived from it -- so an unchanged `MEMORY.md` took the no-op path and its edges were never rebuilt. Since every markdown edge lives in an index, upgrading a pre-0.19 warehouse delivered **zero** of them, and `link_count` stayed stale, until the index text happened to change. The whole feature was a no-op for every existing warehouse. It went unnoticed because every verification rebuilt from scratch, where the bug cannot appear -- the same "flag accepted, exit 0, output byte-identical" class this project's CLAUDE.md warns about, walked into while writing the rule against it. Links are now re-derived when the stored edge set differs from what the current parser extracts, **without opening a version**: the memory did not change, our reading of it did, and asserting an edit that never happened would corrupt the history of every memory in the corpus at once. `link_count` is corrected with them, so the denormalised copy cannot disagree with the bridge table.
- **`created_at` was NULL forever on any migrated warehouse.** The DDL declares `DEFAULT current_timestamp`, but `ALTER TABLE ... ADD COLUMN` carries no default and the INSERTs relied on the table default -- so every row written to an upgraded `dim_memory` / `bridge_memory_link` silently diverged from a freshly built one. Both timestamps are now written explicitly. The upgrade-path test previously asserted only that the column existed, not that anything landed in it.
- **Pre-0.19 bridge rows could never resolve again.** `link_syntax <> 'markdown'` is NULL for rows written before the column existed, so the wiki branch skipped every legacy row permanently: a dangling `[[link]]` whose target was written later would stay unresolved forever. Now `IS DISTINCT FROM`, plus a migration backfill setting historical rows to `wiki` -- matching the `run_kind` backfill precedent, which existed and was not followed.
- **`Ctrl-C` during the memory import was swallowed.** `except BaseException` caught `KeyboardInterrupt`, recorded a failed run and returned, letting the archive continue to `batch.complete()` -- discarding the user's interrupt. Now mark-and-propagate for `KeyboardInterrupt`/`SystemExit`, matching `BatchRun.__exit__`; ordinary exceptions are still recorded and swallowed.
- **Agent memory links could cross repositories.** Link resolution matched on `scope` + `owner_key` + `file_name` with `LIMIT 1`, but `owner_key` is deliberately not unique for agent scope -- which is exactly why `memory_id` carries `owner_root`. Two repositories each holding a committed `reviewer` agent produced two candidate targets, so one repo's index could point at the other's memory. Both resolvers now join back to the source row and require a matching `owner_root`.
- **`record_source` bypassed the provenance allow-list.** `lineage.py` keeps `_RECORD_SOURCES` specifically to catch a typo before it lands in 100k rows, and `record_source_label()` is the gate; the memory import wrote a value straight past it -- and wrote the run's `source_path` sentinel rather than a source label. Added `claude_code_memory` to the allow-list and routed through the validator.
- **The archive's memory scoping ran outside any recorded boundary.** Resolving the home directory and querying `dim_project` / `dim_session` for scope happened at the call site, so a raise there escaped the enclosing `BatchRun` and would abort an archive whose sessions had all already been processed -- the failure shape the natural-key repair docstring cites as having killed a whole `ccutils all` invocation. `run_memory_import` now takes a `resolve_kwargs` callable so that work happens inside the guard.
- **`semantic_etl_runs` did not expose `run_kind`.** The column was added to `fact_etl_runs` to scope the batch rollup (a reconciliation run is a child run that is not a session) but never surfaced in the documented observability view, so the view could not distinguish the two and an unqualified count over it silently mixed them. Now three kinds exist -- `session`, `reconciliation`, and the new `global_source` used by the auto-memory import -- which makes the omission actively misleading rather than merely incomplete. Found by querying a real warehouse for the memory import's run row and getting a binder error on the column that `fact_etl_runs` has carried since it was added.
- **Four populator joins read soft-deleted `fact_tool_results` rows.** `fact_file_operations`, `fact_agent_delegations`, `dim_session_heuristics` and `fact_plan_revisions` all joined `fact_tool_results USING (tool_use_id)` with `is_deleted` filtered on the LEFT side only, so a soft-deleted duplicate result row -- exactly what `_repair_duplicate_natural_keys` leaves behind on an upgraded warehouse -- fanned the join out. In the two lineage-asserted populators that produced duplicate inbound keys and killed the session's ETL (observed: 3 sessions failed on the real upgrade, with 7, 2 and 1 duplicate keys); in the heuristics rollup it would silently double-count `tool_count`/`error_count` with no assertion to catch it. The filter now lives in each join's ON clause. Found by the same upgrade-path test as the resurrection fix below -- the two defects masked each other: while the UPDATE revived the twins, the joins never met a soft-deleted row.
- **`lineage_upsert`'s UPDATE resurrected repaired duplicate rows.** The UPDATE matched `tgt.natural_key = im.natural_key` alone -- every physical row sharing the key, including twins `_repair_duplicate_natural_keys` soft-deleted on open -- and its SET includes `is_deleted = FALSE`, so one hash change per key revived them all. Any hash-schema change triggers it warehouse-wide: upgrading a pre-fix warehouse on current code (which added `agent_resolved_model` to `fact_tool_results`' hash columns) changed every row's hash, one batch run revived all 29 repaired `tool_use_id` twins, and `populate_delegation_completion` died on the resulting fan-out after every session had already been processed -- the repair healed the warehouse at open and the same run un-healed it. Found by re-running the upgrade-path test against a real pre-fix warehouse (a fresh rebuild can never catch this class; that is now twice in three days). The UPDATE now addresses exactly one physical row per key: the live row, else the lowest-rowid soft-deleted one -- which keeps legitimate revival working, since the INSERT's `NOT EXISTS` matches deleted rows and the UPDATE is the only path back. Verified end-to-end: the same upgrade re-run completes exit 0 with zero live duplicate keys across all 13 facts. One response containing thinking + text + tool_use blocks is flushed as several assistant JSONL entries, each repeating the same `message.id` and the same `usage` object. `fact_token_usage` keyed per entry, so a split response counted 2-3 times: on a real corpus, 7,088 usage-bearing entries stood for 3,449 responses and `fact_session_summary.total_output_tokens` over-reported by **2.47x**. Now `fact_token_usage` QUALIFYs to the first entry per `(session_id, api_message_id)` -- `message.id`, falling back to `requestId`, then `entry_id` so pre-2025 transcripts without the field keep per-entry identity instead of collapsing a session into one row -- and `fact_messages` populates its token columns only on the response's first entry (NULL on continuations; the stored `api_message_id` distinguishes "continuation" from "no usage captured"). `api_message_id` is deliberately NOT the natural key: ~1.4% of response ids recur across session files because resume/fork replays history, and a cross-session natural key would merge two sessions' rows. `entry_id` remains the key with a deterministic survivor, so re-ETL is a no-op rather than a soft-delete/re-insert churn. Downstream, `agent_derived_io_tokens` (which sums `fact_messages` tokens over the agent's session) drops accordingly on rebuild -- it was summing the over-count; the 2026-08-02 conclusion that it is not comparable to the API's stated `totalTokens` is unchanged and strengthened. Existing warehouses heal on the next batch run: every session re-stages, the deduped inbound soft-deletes the stale per-entry rows (verified against a real pre-R23 warehouse -- see the log for the measured before/after).
- **`--no-thinking` was silently ignored by the HTML exporter.** `generate_html` had no `include_thinking` parameter at all, so `ccutils local --format html --no-thinking` exited 0 and produced output **byte-identical** to the default, with every thinking block rendered; `export/markdown.py` honoured the same flag, so the two render formats disagreed silently on the same option. The batch path was equally affected -- `generate_batch_html` neither accepted nor forwarded it. Measured on a real session: 6 thinking blocks rendered under `--no-thinking`, now 0. This is the failure CLAUDE.md's rule names verbatim ("assert the flag's actual effect (sanitized paths, absent thinking), not just acceptance"), and it is the same silent-no-op class as the `--private` regressions. Thinking blocks are now removed from the loglines up front, before any consumer sees them, rather than by threading a flag down to `render_content_block` -- one auditable place, so no render path (transcript body, conversation stats, index) can reintroduce the content by another route. `redacted_thinking` is stripped alongside `thinking`: it still carries an Anthropic-side summary and is rendered, so omitting it would leave the flag half-honoured. Tests assert the effect on rendered output and end-to-end through the CLI, plus a non-vacuity control that thinking IS present by default.
- **The re-derived async delegation tokens were a different measure from the API-stated ones, in the same column.** Corpus validation of the completion pass (below) scored every derivation against ground truth: 188 synchronous delegations carry both an API-stated rollup and an ingested agent transcript, so the async derivation can be run where the true answer is known. Duration matched 188/188 and tool-use count matched 188/188 -- but tokens matched only **12/188 within 10%**, with the per-row ratio spanning p10 0.063 to p90 1.004. No formula reconciles the two (in+out, out alone, +cache_creation, +cache_read, `total_uncached_equivalent`, the 5m/1h cache splits); it is not a capture gap (median 23 assistant records, 23 carrying usage) and not a nested-subagent rollup (all 188 spawned none). They count different things. - **`_repair_duplicate_natural_keys` and the projection `QUALIFY` now skip NULL keys**, matching `lineage_upsert`, which already excluded them. SQL groups every NULL into one bucket, so both would have collapsed unrelated NULL-key rows to a single survivor. Unreachable today -- every natural-key column is `NOT NULL` at the DDL level -- but the three places that reason about key uniqueness must agree, or whichever one was overlooked breaks the first time a nullable key appears. The repair's docstring also no longer claims the lowest-rowid survivor is reproducible across warehouses: DuckDB implements UPDATE as delete+reinsert, so rowid reflects update history rather than insertion order. The choice is arbitrary, and harmless only because the known duplicates are content-identical.
- **A projection now emits the grain its populator declares, and `lineage_upsert` asserts rather than repairs it.** The natural-key fix below first landed as a generic collapse inside `lineage_upsert` -- the wrong layer. A duplicate key means the populator's projection does not produce the grain it declares, and only that populator knows whether collapsing is safe or which row should survive; resolving it in shared machinery applied one fact's judgment to all 13 and did so invisibly (the step counts could not distinguish a collapse from an unchanged row -- on a full rebuild `fact_tool_results` read 76,166 / inserted 75,397 / updated 33, a gap of 736 against roughly 72 rows actually removed). Investigating the root cause also disproved the stated one: there is **no populator fan-out**. Zero entries carry two `tool_result` blocks for one `tool_use_id`; all 29 violations are a single `tool_use_id` recorded under two distinct entry uuids, and the duplicate records are content-identical on every extracted column (`is_error`, `result_content_text`, `timestamp`, `tool_name`, and every typed `bash_*`/`edit_*`/`read_*`/`agent_*` field) -- only the raw `result_payload_json` ever differs, on 8 of 29. So the data model was correct all along: `tool_use_id` is the right natural key and the grain is right. `_PROJECT_USES_SQL` and `_PROJECT_RESULTS_SQL` now `QUALIFY` to one row per `tool_use_id` with that justification stated inline; `fact_file_operations`, `fact_tool_chain_steps`, `fact_errors` and `fact_agent_delegations` inherit uniqueness because they derive from those two. `lineage_upsert` now raises a `ValueError` naming the table, key and count instead of collapsing, so a future populator with a fanned-out join fails loudly rather than silently double-counting. That also removes a hazard the collapse carried: dropping a row could drop its `session_id` from the soft-delete scope, leaving stale rows for that session soft-deleted never.
- **`lineage_upsert` did not hold the natural key it declares.** Its INSERT guards with `NOT EXISTS (SELECT 1 FROM tgt WHERE tgt.key = im.key)`, which consults only the TARGET, so two inbound rows sharing a natural key both passed the check and both inserted. The helper's docstring stated "one row per natural key" as an inbound contract and nothing enforced it. On a real 2,344-session corpus **6 of the 13 facts that declare a natural key were violating it**: `fact_tool_results` 29 keys, `fact_file_operations` 8, `fact_tool_uses` 7, `fact_tool_chain_steps` 7, `fact_agent_delegations` 3, `fact_errors` 1. Consequences were silent: any consumer joining on a declared key fanned out, which is how 3 duplicate `delegation_key` rows appeared in a table whose key is unique per (session, tool use) by construction. The fix is described in the entry above -- the projection produces the grain, the helper asserts it. (An interim version of this fix collapsed duplicates inside `lineage_upsert`; that mechanism was removed in the same release and never shipped.)
- **Warehouses built before that assertion heal themselves on open.** The assertion stops new duplicates but does nothing about rows already stored, and those are not inert: several populators build their inbound batch by reading a TARGET fact table, so a stale duplicate propagates into a new inbound and trips the raise. The severe case is `populate_delegation_completion`, whose inbound is the whole `fact_agent_delegations` table and which runs from `run_post_session_reconciliation` **outside** any per-session `try/except` -- one stale duplicate anywhere killed an entire `ccutils all` invocation after every session had already been processed. Reproduced against a real pre-fix warehouse holding 3 duplicate `delegation_key` rows. `create_star_schema` now runs `_repair_duplicate_natural_keys` after column migrations, soft-deleting all but the lowest-rowid row per declared key (non-destructive, matching the warehouse's lineage convention, and deterministic so two identically-seeded warehouses heal identically). Verified on that warehouse: 55 violating keys across 6 facts to 0, and the reconciliation completes. A clean warehouse pays only one guarded existence check per fact. New `NATURAL_KEYS` map in `schemas/star/schema.py` is the single source of truth the repair walks, with a test asserting it cannot drift from what the populators declare.
- **Background-launch acknowledgments were recorded as delegation completions.** Since Claude Code v2.1.198+ subagents run in the background by default, so the tool result returned at spawn time is a launch acknowledgment rather than an outcome. On a real corpus 719 of 941 delegations (76%) are `async_launched`, and on those rows three columns held values that read as valid and were not: `seconds_to_completion` (median 2.05s -- the acknowledgment latency -- against 102.45s on the 192 rows that actually completed), `completion_timestamp` (the acknowledgment's timestamp, milliseconds after the spawn), and `agent_output_text` (the literal string "Async agent launched successfully."). Nothing in the row marked which kind it was, so any aggregate silently blended the two, biased toward under-reporting exactly the long-running expensive delegations. All three are now NULL when the result is a background launch, detected via the newly-captured `agent_is_async` (from the stated `toolUseResult.isAsync`, which like `is_error` is only ever written as true). Re-deriving the true metrics from the subagent's own transcript is separate work -- see `internal/plans/2026-08-01_agent_delegation_capture_gap.md`, filed from the consuming side.
- **`fact_agent_delegations.agent_session_key` was NULL on every row** (941 of 941 on a real corpus), so no delegation could be joined to the agent session it spawned -- while 826 of those rows carried a `subagent_type` and 936 agent sessions sat unlinked. The column resolved through a correlated subquery on `dim_session.agent_id`, which only finds a row if the agent's own transcript has already been ETL'd; ETL is per-session and a parent is normally processed before its agents. It was also excluded from the populator's hash columns, so a later run could never repair it (hash unchanged, no update). Now derived from the natural key as `md5('agent-' || agent_id)` -- `session_key` is `md5(session_id)` and an agent's `session_id` is `'agent-' || agent_id` -- which needs neither a join nor an ordering guarantee, and added to the hash columns so rows written by earlier versions heal on re-run. The key may reference a session that was never ingested (30 of 880 on the real corpus); that is the normal degenerate-key case and consumers already LEFT JOIN.
- **`fact_plan_revisions` labeled accepted plans `unknown`.** The outcome logic read `is_error IS NULL` as ambiguous and fell back to matching an approval phrase in the result text, bucketing anything else as `unknown`. But an omitted `is_error` means not-an-error: Claude Code writes `is_error: true` on failure and encodes success as either `false` or an absent field, which the API defines as equivalent. Measured across 71,635 tool results (2,331 TRUE / 31,269 FALSE / 38,035 NULL), and on `ExitPlanMode` specifically (2 TRUE / 6 NULL / 0 FALSE). - **`fact_tool_chain_steps` produced no chains at all.** A chain was defined as the tool uses sharing an assistant `message_id`, but `fact_tool_uses.message_id` is the per-entry JSONL uuid and Claude Code writes ONE content block per assistant entry -- parallel tool calls become separate entries sharing an API message id while carrying distinct uuids. Rebased the grain onto the *agentic run*: the contiguous tool uses following one human turn, up to the next. `time_since_prev_seconds` is now genuine elapsed time (median ~4.6s on the real corpus). ### Added
- **Claude Code auto memory is ingested end-to-end into the warehouse** -- `dim_memory` (Type 2 SCD), `bridge_memory_link`, and the `semantic_memory` / `semantic_memory_links` views. Auto memory is the markdown Claude writes to itself under the per-project `memory/` directory and the subagent `agent-memory` directories; nothing in ccutils read it before, so the corpus was invisible to the warehouse despite being the highest-density statement of what Claude has learned about a project. All three documented subagent scopes are covered (`user`, committed `project`, gitignored `local`) alongside project memory.

  **Type 2, because nothing else keeps the history.** Claude Code overwrites memory files in place: the `modified:` frontmatter field records only the last write, and earlier contents survive solely in `file-history` rollback checkpoints, which are pruned (on a real machine those reach back ~3 months against 7 months of sessions). Storing one row per file would have made every re-ingest destroy the previous state, so a row is one VERSION -- `memory_id` is the file's stable identity, `memory_key` one version of it. Version identity is `(memory_id, version_num)` and deliberately **not** `(memory_id, content_hash)`: a memory reverted to earlier text repeats its hash, and keying on content would silently drop the revert. `content_hash` covers name/description/type/node_type/origin + body and **excludes** the `modified:` stamp, which Claude Code rewrites on every write -- hashing it would open a spurious version on every touch, filling the history with rows that differ only by a timestamp.

  Two subtleties that would each have produced silently wrong history. A memory file that disappears is **closed, not deleted** (`is_current = FALSE`, `valid_to` set) -- a retired memory is a fact about the project's history, and erasing the row would make the warehouse forget it ever existed. Retirement keys off the owners that were *scanned* rather than the files that came back, because those differ exactly when a memory directory is emptied: keying off results there would leave every one of its rows marked current forever, while the scanned-owner scoping simultaneously stops a filtered run (`-p mitate`) from retiring another project's memory as collateral. Both cases are tested.

  Memory identity is `md5(scope || agent_scope || owner_root || owner_key || file_name)` and every part earns its place -- memories that merely share a file name must not collapse into one row that appears to flip-flop between bodies on each import. Three collisions this prevents, all reachable: a project's `MEMORY.md` against a subagent's, the same subagent declared `memory: user` in one place and `memory: project` in another, and a committed `reviewer` agent existing in two repositories (ordinary, since committed subagent memory is shared with a team). `owner_root` is NULL for project scope, where the encoded directory name is already globally unique. Retirement scoping matches at the same granularity, so scanning one repository cannot retire another's identically-named agent memory.

  **The import is a recorded ETL run, not a bare call.** `run_memory_import` wraps it in an `EtlRun` with `run_kind = 'global_source'` and a `dim_memory` step, following `run_post_session_reconciliation`. Memory is a per-repository source so it cannot live inside `run_v15_etl` -- but that is a reason to run it after the per-session loop, not a reason to run it outside the three-grain run-metadata system every other populator reports into. A global source writing rows without a run is invisible: nothing reports how many versions a run wrote, no row says which run observed it, and a failure leaves no trace at all. Rows carry `created_at` / `created_by_version_key` / `etl_run_id` / `record_source`, so the provenance question a Type 2 SCD actually raises -- "which run observed this version" -- has an answer. They deliberately carry no `is_deleted` (that would be a second deletion mechanism competing with `is_current`/`valid_to`) and no `hash_diff` (`content_hash` is the change detector). Failures are recorded rather than raised: the run row carries the error and the archive completes, since memory is additive -- but the previous `except Exception: pass` is gone, because a swallowed failure left a warehouse indistinguishable from one built where auto memory was disabled.

  The provenance and `link_syntax` columns are appended to `_COLUMN_MIGRATIONS`, because the memory tables landed in an earlier commit without them and `CREATE TABLE IF NOT EXISTS` never widens. This is not the usual cosmetic case: the import writes those columns directly, so an un-migrated warehouse would fail on a missing column rather than blank a field, and `_resolve_link_targets` branches on `link_syntax`, so every index edge would fall through to identifier matching and silently resolve none. Verified by a control -- with the migration entries removed, all three upgrade-path tests go red.

  Ingestion is scoped to the projects already in `dim_project`, so a filtered archive run does not pull in the whole machine's memory corpus. `project_key` resolves via `dim_project.project_name` (the encoded `projects/` directory name, which is exactly the memory directory's owner); `session_key` resolves from the `originSessionId` frontmatter field, and an unresolvable one degrades to NULL while the raw id survives -- it is the only evidence of which session wrote the memory. Frontmatter is parsed without adding a YAML dependency: every line in the observed corpus is a plain `key: value` with at most one level of nesting, and both shapes found in real corpora are read (newer files nest under `metadata:`, ~17% of files predate it and carry a top-level `type:`; reading only the new shape would blank `memory_type` for a sixth of the corpus). Files with no frontmatter at all -- typically the `MEMORY.md` index -- fall back to the file stem.

  `bridge_memory_link` records the link graph, one row per link OCCURRENCE per version, so each version owns its edges and the graph is queryable as of any point in time. **Both link syntaxes are read**, and `link_syntax` keeps them apart: `[[name]]` is the prose cross-reference between topic files, while `[Title](file.md)` is how `MEMORY.md` indexes the topic files below it. Reading only the wiki form would drop every index edge -- the relationship that makes the corpus an index rather than a pile of files; measured on a real corpus, 71 of 140 edges were markdown links, all 71 originating in an index, and 70 duplicated no wiki edge. `link_text` captures the index's own label for each target, which is not recoverable from the target file.

  The two resolve differently because they name different things. A markdown target is a file name the author wrote as a path, so it matches `file_name` exactly -- running it through name/stem matching could match a memory whose frontmatter `name` merely resembles the filename while ignoring the one unambiguous thing supplied. A wiki target is an identifier, matched against the frontmatter `name` or the file stem (both occur and routinely disagree: `notes_archive.md` carries `name: archive-notes`), modulo separator since `-` and `_` are the same identifier in different clothes. Still an exact match on a normalised string -- prefixes and substrings are deliberately not matched, since a link that resembles a memory without naming it is authoring drift and guessing would invent edges the author never wrote.

  Links inside fenced code blocks are excluded (a fence showing the syntax is documentation, not an edge), as are external URLs, in-document anchors, images and paths reaching outside the memory directory. `ordinal` is document order across both syntaxes. Dangling links are retained with `is_resolved = FALSE`: a link to a memory that was never written marks something Claude meant to record, which dropping the row would hide.
- **`semantic_context_growth` view (R23)** -- per-request context-size deltas within a session. `context_tokens` is `total_uncached_equivalent_tokens`, the exact prompt size the API saw, so diffing it across consecutive requests prices everything that entered the context between two assistant turns -- the only exact handle on tool_result cost, since tool results carry no `usage` of their own and are the bulk of transcript text. `inbound_tokens` nets out the previous response's own output re-entering as history; compaction shows as `is_context_reset` with `inbound_tokens` suppressed rather than booked as a large negative. Slightly negative values without a reset are real (thinking bills as output but is not retained in later context) and left visible. The view is only meaningful on the R23 response grain -- against the per-entry grain, 51% of deltas came out negative.
- **`fact_agent_delegations.completion_state` and re-derived async rollups.** The honesty fix above NULLed the misleading acknowledgment values but left 721 of 943 delegations (76%) with no metrics at all. Those metrics were never missing from disk -- the subagent's transcript is ingested as its own session and already carries usage, timestamps and `stop_reason`. A new post-loop pass (`populate_delegation_completion`) re-derives tokens, duration, completion timestamp and tool-use count from the agent's OWN session rows, so the backfill is retroactive over the existing corpus with nothing re-read from disk. `completion_state` distinguishes `completed` (terminal `stop_reason` on the agent's last assistant record), `no_completion_recorded` (the agent's transcript records no completion), and `spawn_failed` (the agent was never created -- fork-inside-fork, subagent depth limit, cancellation, validation error, user rejection; 29 of the 30 NULL-`agent_status` rows on a real corpus, separated from the 30th by a stated `is_error` rather than by matching the result text, because that row is a successful background launch reading "Fork started - processing in background" that merely carried no agentId). Rollups are written ONLY for `completed`: a partial sum from an unfinished agent is indistinguishable from a fast one. `no_completion_recorded` states the observation rather than an inference about liveness -- corpus validation found that of 101 rows first labelled `in_flight_at_ingest`, 98 had ended mid-tool-loop a median of 15.7 days before the ETL ran and only 2 were recent enough to still be running, so the name asserted something the transcript cannot establish. That also retires the reason `abandoned` was withheld: no staleness threshold is needed to say nothing was recorded. Measured limit: ~10% of agents that demonstrably finished still land in this state (19 of 188 whose parent saw a synchronous result), and two alternative completion predicates miss exactly the same 19, so the shortfall is in the transcripts rather than the test. Synchronous delegations keep their existing parent-side metrics untouched. This runs as a cross-session pass rather than inside the per-session populator because sessions are ETL'd in arbitrary order and a parent is normally processed before the agent it spawned -- the same ordering trap that left `agent_session_key` NULL on every row.
- **`fact_etl_runs.run_kind`** -- `session` or `reconciliation`. `fact_etl_runs` was one-row-per-session by construction, so `BatchRun.complete` counted child run rows as sessions; the cross-session reconciliation pass is a child run that is not a session, and without a discriminator every batch reported one more session than the CLI actually processed. Mirrors `fact_etl_steps.step_kind`, which exists to scope the fact rollup for the same reason. Stamped at INSERT rather than at completion so a run that crashes is still classified, preserving the rollup's treatment of crashed sessions as failed ones. Historical rows backfill to `session`.
- **`fact_tool_results.agent_resolved_model` / `fact_agent_delegations.agent_resolved_model`** -- `toolUseResult.resolvedModel` is the model a subagent ACTUALLY ran on, and the parent's delegation row is the only place it is stated: 894 of 2,046 agent sessions on a real corpus have no ingestible transcript of their own, so their model was otherwise unknowable. 815 such values sat in the corpus captured nowhere. Note the value can carry a context-window suffix (`claude-opus-4-8[1m]`).
- **`dim_model.model_base`** -- the model id with its context-window suffix stripped (`claude-opus-5[1m]` -> `claude-opus-5`). `model_name` stays byte-faithful to the transcript; without a base column the two become separate `dim_model` rows and every per-model aggregate splits silently the first time a variant appears.
- **`dim_tool.tool_category` is populated.** The column shipped in the DDL with the comment "categorization left to a heuristic pass" and nothing ever filled it -- all 52 tools on a real corpus read `unknown`. Single source of truth is `TOOL_CATEGORY_SQL` in `etl/utils.py`, used both for newly-inserted tools and to backfill pre-existing `unknown` rows. The mapping is definitional (Read reads, Edit mutates, Bash executes), not inferred; MCP tools match the `mcp__` naming convention rather than being enumerated, so a new MCP server needs no code change. Categories: `read`, `search`, `mutate`, `execute`, `web`, `delegate`, `plan`, `interact`, `mcp`, `other`.
- **Tier 1 facets F30 `tokens_out` and F31 `thinking_blocks`.** F15 (`tokens_in`) shipped with no output counterpart, and deliberation depth was reachable only through `fact_session_summary`, which Tier 1 must not depend on because the summary populator runs last. On a real corpus these two separate behavior archetypes that tool mix alone cannot -- median output tokens 47,533 for edit-heavy sessions vs 2,849 for read-heavy, median thinking blocks 24 vs 0. Note the Tier 1 facet range is now non-contiguous: F01-F19 plus F30-F31, with F20 remaining the Tier 2 LLM facet.
- **`semantic_session_behavior` view** -- the per-session behavioral feature vector: tool-category counts and shares, agentic-run shape (`agentic_runs`, `tools_per_run`, `median_gap_seconds`), tokens in/out, thinking blocks, error rate, and a `PERCENT_RANK()` column per discriminating feature. Deliberately carries no archetype label and no threshold: cutoffs that turn features into categories belong in the analysis layer, derived from the corpus distribution, and a test asserts no column name contains `archetype`/`label`/`bucket` so classification cannot leak back into the schema. Design rationale and the plan for replacing the keyword `intent` classifier: `internal/plans/behavior_analytics.md`.
- **Sessions whose `cwd` resolves under the OS temp directory are excluded from discovery by default** (`find_all_sessions`, `find_local_sessions_rich` in `parsers/discovery.py`; new `is_temp_dir_cwd` predicate). Sandboxed/ephemeral tooling (eval harnesses, CI scratch runs) writes real Claude Code session files under paths like `/private/tmp/<...>`, and on a real corpus these can outnumber genuine projects by an order of magnitude -- crowding the interactive picker and, if ever batch-ingested, polluting session counts and facets with synthetic, non-representative activity. New `--include-temp-sessions` flag on `ccutils local` / `ccutils all` opts back in. `extract_session_metadata` now also returns `cwd`, captured independently of the sessionId-bearing line it returns (some entry types, e.g. `queue-operation`, carry `sessionId` without `cwd` and can precede the entries that do).
- Archive-scanning canary asserting no `claude-*` model id in the archive falls through to `model_family = 'unknown'` -- the structural parse means a new family classifies itself, but a naming-convention change would still land silently in a bucket that reads as a rounding error, which is exactly how `claude-fable-5` hid.
- Archive-scanning canary asserting `is_error` is only ever `true`, `false`, or absent -- a third encoding (notably an explicit null meaning "unknown") would silently reroute every error count, because the tri-state CASE in `fact_tool_calls.py` coerces rather than fails. Deliberately does NOT assert "only Bash writes false": that held across the corpus but is incidental (a `Workflow` result writes it too, harmlessly, since false and absent are equivalent), and encoding it would break on correct data.
- Behavior tests for `semantic_tool_patterns` -- the only semantic view that had no test coverage (frequency aggregation, error counts, and the `HAVING >= 2` threshold).
- Project skills under `.claude/skills/` (`query-warehouse`, `etl-dev`, `render-exports`): a progressive-disclosure hierarchy of task-scoped guidance with on-demand reference files; `.gitignore` narrowed so the skills are tracked while the rest of `.claude/` stays local.

### Changed
- **HTML export is one self-contained file per session, and the batch archive is flat.** Previously a session rendered as a directory of paginated `page-NNN.html` files, and `ccutils all` built a master index -> per-project index -> per-session tree with a separate `search-index.js` carrying the full text of every session. Pagination existed to keep pages small, but it forced in-session search to `fetch()` sibling pages -- which browsers block on `file://`, and the `.catch()` swallowed the error, so search reported "0 results" indistinguishably from no matches for anyone who opened the export the normal way. Now: one `.html` per session with CSS and JS inlined and pinned by sha256 in a strict CSP (`default-src 'none'`, never `unsafe-inline` -- a hash covers a block, so `style=`/`on*=` attributes stay forbidden everywhere), `content-visibility: auto` doing the work pagination was doing, and a single filterable `index.html` where a project is a filter over one list rather than a page. Measured on the largest real session: 26.4 MB of JSONL renders to a single 14.9 MB file in 0.3s, confirmed working in a browser. In-page navigation is a collapsible prompt list plus a client-side filter box; no shipped JS makes any network call (guarded by test). `--no-search-index` is accepted and ignored for compatibility -- there is no search index to skip. Cross-session full text lives in the warehouse, where DuckDB fts belongs.
- **The transcript prompt list drops harness-injected prompts by their stated `promptSource`.** Claude Code stamps user entries with `promptSource` (`typed`/`sdk`/`queued`/`system`); `system` marks machine-generated payloads (task notifications) that rendered as navigation entries in the prompt list. The parser now preserves the field and the renderer skips `system` rows in the list only -- the entries still render in the transcript body. Measured before acting on the field: "Stop hook feedback:" prompts do NOT carry `promptSource: "system"` (2 `typed`, 7 with no field on a real corpus), so the existing literal check remains alongside the field check rather than being replaced by it.
- **HTML export renders markdown with `markdown-it-py` (`html=False`) instead of Python-Markdown.** Python-Markdown passes raw HTML through by design, so `nh3` was *stripping* it -- which silently deleted transcript content. A prompt reading `Try <script>console.log(1)</script> here` rendered as `Try  here`, and `Wrap it in <div class="panel"> for layout` rendered as `<p>Wrap it in </p><div> for layout<p></p></div>` with the text gone and the paragraph split. Transcript text is data, not authored HTML: the correct behaviour for an archive is to *escape* raw HTML so it displays as what was written. markdown-it-py's `js-default` preset does that by construction and additionally rejects `javascript:`/`vbscript:`/`file:`/`data:` link targets. `nh3` is retained as defense in depth -- with `html=False` it should find nothing to clean, and that is precisely why it stays: it does not depend on the renderer config remaining correct. Two existing tests asserted `"alert(" not in result` and `"onerror" not in result`, which encoded *strip* semantics and would fail on the correct behaviour; they now assert the durable claim (never appears as **markup**) rather than the incidental one (never appears). Side effect worth noting: markdown-it-py is CommonMark and Python-Markdown is not, so an ordered list may now interrupt a paragraph -- `I should:` followed immediately by `1.` previously rendered as run-on text and now renders as a real `<ol>`, which models emit constantly.
- Bare runtime dependencies now carry version floors (`click`, `click-default-group`, `duckdb`, `httpx`, `jinja2`, `questionary`). An unpinned dependency states no minimum supported version.

### Changed (tests)
- **The 18 HTML snapshot baselines are replaced by explicit assertions and invariants.** `tests/__snapshots__/*` was gitignored, so the baselines only ever existed on the machine that generated them: a fresh clone or CI saw 18 failures, and "full suite green" was true nowhere else. An untracked snapshot is not a test, it is a cache of the last run's output with a green checkmark -- and a baseline regenerated with `--snapshot-update` silently absorbs whatever the code did at that moment, which is how it was cited repeatedly as corroborating evidence it could not provide. Fourteen block-level snapshots (thinking/text/tool-result blocks, the tool renderers) became direct assertions on the contract they were actually checking -- never snapshot what you can assert. Four page-level snapshots were dropped; they cover a layout that is about to be rewritten, so their baselines were worthless as a safety net during exactly the change that most needs one. `syrupy` removed from dev dependencies. Every new assertion was spot-mutated to prove it can fail: dropping the `nh3` `code`-class carve-out and renaming the `thinking` CSS class each turn the suite red.
- **New invariant: the HTML and markdown exporters must agree on `--no-thinking`** (`TestExportersAgreeOnThinking`). This is the invariant the shipped bug violated -- markdown honoured the flag, HTML ignored it, and each exporter's own tests passed because the defect lived between them where nothing was looking. A per-exporter test cannot catch that by construction. Verified by reintroducing the exact bug (flag accepted, no effect): the new test fails, the old per-exporter tests do not. Carries a non-vacuity control asserting both exporters DO emit thinking by default, so the absence assertions cannot pass because nothing rendered.

### Removed
- **The `explore` command and the `ccutils[explore]` extra.** It was 29 lines of `subprocess.run(["harlequin", db])`. DuckDB ships its own local UI (`duckdb -ui <database>`), which is a better SQL notebook than anything worth wrapping and needs no Python dependency at all. The wrapper also had a measurable cost: harlequin pins `click==8.1.8`, `rich-click==1.8.5` and `questionary==2.0.1` as hard equalities in every version including the current one, so an optional extra dictated the version of three direct dependencies for the whole project -- and bumping harlequin was unresolvable against `questionary>=2.1.1`. Removing it moved `click` 8.1.8 -> 8.4.2 and dropped `rich-click` from the graph entirely. README points at `duckdb -ui` instead. Note `classify_intent` still returns an `explore` intent category; that is unrelated to the command.
- **Pagination and the fetch-based search layer.** Templates `page.html`, `base.html` (dead once every document became standalone), `search.js`, `global_search.js`, and the generated `search-index.js` are gone, along with per-project directories in batch output. See the self-contained-file entry under Changed for why; the security claims those files carried (no unsafe `innerHTML`, no `unsafe-inline`, strict `default-src`) moved to tests over the surviving surfaces (`filter.js`, `static/transcript.js`, `_build_csp`) instead of being deleted with them.
- `black` from the dev dependency group -- declared with no config section, no pre-commit hook, and no invocation anywhere in the repo. `pytest` and `pytest-httpx` are retained: they are imported by 53 and 2 test files respectively and `uv run pytest tests/` does not run without them. (`syrupy` was retained by this change and later removed with the snapshot baselines -- see Changed (tests).)

### Fixed
- **Subagent depth propagation now runs on every ETL call, and only touches the current session's tree.** Two defects in `_propagate_depth_level`: (1) it globally reset + recomputed `depth_level` for the ENTIRE `dim_session` on every per-session ETL -- O(N^2) writes across a batch on the persistent warehouse (deferred finding #3 from the 2026-07-10 review); (2) it only ran at all when the current session WAS a subagent, so a parent session landing after its children never re-rooted them -- the children kept `depth_level = 0` forever. The recompute is now scoped: walk UP from the staged session to its root, recompute DOWN through that root's subtree, leave unrelated trees untouched. Regression tests: `test_parent_arriving_after_child_fixes_child_depth`, `test_unrelated_tree_depth_untouched_by_new_session`.

### Fixed (post-review)
- **Tier 2 facets are no longer destroyed by a failed re-extraction.** `populate_tier2_facets` now scopes its soft-delete to sessions that actually produced rows this run (`session_id IN _INBOUND`), not every session in staging. Previously, re-ETLing a session with `--with-llm-facets` while the LLM API was failing left the inbound empty, and the widened staging-based soft-delete marked the session's existing good facets `is_deleted=TRUE` -- data loss from a transient failure. Tier 1 (deterministic, always emits a row per session) keeps the default scope. Regression test: `test_failed_reextraction_preserves_prior_tier2_facets`.
- **`ccutils local --format duckdb/json` no longer aborts on one empty/unparseable session.** The single-file export looped `run_v15_etl` with no error handling, so a session with no valid entries (which now raises `ValueError` from `write_session_to_parquet`) crashed the whole command with a traceback and leaked the connection. ### Removed (post-review)
- **`stg_task_agent_map` dropped.** The staging table was created, cleared by `staging_scope`, and listed in the JSON export, but no populator ever wrote to or read from it -- vestigial infrastructure. Removed the DDL, the `staging_scope` DELETE, the `json_export` entry, and the three e2e assertions that vacuously checked it stayed empty (they passed regardless of ETL behavior). The redundant `--no-thinking`-only `DELETE FROM stg_log_entries` in `run_v15_etl` is also gone: `staging_scope` clears staging unconditionally, so raw thinking never survives the run regardless of the flag.

### Changed
- **The star schema is now a persistent, incrementally-updatable warehouse.** Every table in `create_star_schema()` switched from `CREATE OR REPLACE TABLE` to `CREATE TABLE IF NOT EXISTS`, so re-running the CLI accumulates sessions instead of wiping the warehouse each run. Aggregate/rollup populators are now scoped to the current session so a persistent warehouse doesn't get rescanned or clobbered: every rollup CTE in `fact_session_summary` and the soft-delete in `lineage_upsert` gate on `session_id IN (SELECT session_id FROM stg_log_entries ...)`, and `run_v15_etl` wraps its body in a `staging_scope` context manager that clears `stg_log_entries` + `stg_task_agent_map` on exit (staging is always cleared now, not only under `--no-thinking`).

### Fixed
